# オセロニア所持駒管理（othellonia-inventory）

オセロニアの所持駒スクリーンショットを **iPhoneのSafariだけ** で解析し、所持駒を管理するPWA（Progressive Web App）です。
画像認識はすべて端末内（ブラウザ）で行い、スクリーンショットや所持駒データを外部サーバー・GitHubへ送信することはありません。

- 月額運用費0円（GitHub Free + GitHub Pagesのみ）
- 通常利用でOpenAI APIなど有料サービスを使用しません
- ChatGPTへの相談は、アプリが生成したテキスト/JSONを**あなたが手動で共有**する方式です

## 公開URL

```
https://<GitHubユーザー名>.github.io/othellonia-inventory/
```

（実際のURLは、このリポジトリのGitHub Pages設定完了後に確定します。下記「GitHub Pagesへのデプロイ手順」を参照してください。）

## iPhoneでの使い方

### 1. 開く・ホーム画面に追加する

1. iPhoneのSafariで上記の公開URLを開く
2. 共有ボタン（□に↑）→「ホーム画面に追加」を選ぶと、アプリのようにアイコンから起動できます

### 2. スクリーンショットを取り込む

1. ホーム画面下部の「取り込み」タブを開く
2. 「写真ライブラリから選択」をタップし、所持駒一覧のスクリーンショットを複数選択
3. 「認識開始」をタップすると、駒アイコンの切り出し枠（緑色の四角）がオーバーレイ表示されます。
   ずれている場合は開始位置・行間隔・列位置などの数値を調整してください
   （調整値は同じ画面サイズの端末で次回以降も使われます）
4. 「この設定で認識開始」をタップ（この処理は端末内だけで行われ、画像はどこにも送信されません）
5. 処理中は進捗が表示され、必要であればキャンセルできます

### 3. 認識結果を確認する

1. 自動的に「認識結果」画面へ移動します
2. 信頼度が高いものは「自動確定」、低いものは「要確認」と表示されます
3. 「要確認」の駒は、候補一覧から選ぶか、「名前で検索」して正しい駒を選び直せます
4. 所持数の修正、「不明のまま保留」「登録対象から外す」も可能です
5. 「所持駒として保存」を押すと、端末内（IndexedDB）に保存されます

一度確定した駒のアイコンは、次回以降の自動認識の精度向上のために端末内へ学習用データとして
蓄積されます（後述「画像認識の仕組み」参照）。

**駒マスタに存在しない駒を検索しても見つからない場合**、「名前で検索」パネルから以下を選べます。

- **新しい駒として仮登録**: 仮の名称を入力して登録します。アプリ内部で一意なpieceIdを新しく発行し、
  切り出したアイコンの特徴量と入力した名称を紐づけて端末内に保存します。以後の自動認識にも使われます
- **不明駒として保存**: 名称が分からない場合、名称未確認のまま所持駒として保存します
- 入力した仮の名称に似た駒（マスタ登録済み・仮登録済みの両方）がある場合、重複登録を防ぐため
  候補として警告表示されます

仮登録した駒は「情報未確認」として扱われ、「駒情報を補完する」画面からAI調査の対象にできます。
AIから返ってきた正式名称・属性・進化形態などは、必ず差分確認画面でユーザーが承認した場合のみ反映されます
（詳しくは次項）。

### 4. 所持駒を編集する

- 「所持駒」タブで一覧を確認できます
- 名称検索、属性（神・魔・竜）、ランク、形態、確認状態で絞り込めます
- 各駒をタップすると、所持数・スキルレベル・確認状態・メモを編集できます
- 「＋ 駒を手動追加」からスクリーンショットを使わずに追加することもできます

### 5. バックアップする（重要）

Safariのサイトデータ削除・機種変更・PWAの再インストールで、端末内のデータは失われます。
**定期的に「バックアップ」タブからJSONファイルを保存してください。**

1. 「バックアップ」タブ →「JSONバックアップを保存」
2. 保存されたファイルは、Files（ファイル）アプリやiCloud Driveなどに保管してください
3. 復元する場合は同じ画面の「バックアップファイルを選択」から読み込みます

バックアップには、攻略サイトの画像やあなたの元スクリーンショットは含まれません（駒ID・名称・所持数・
確認状態などの事実情報のみ）。

### 6. ChatGPTに相談する

1. 「AI相談」タブで相談したい目的（デッキ編成、育成優先順位、ガチャ判断など）を選ぶ
2. 相談対象にしたい所持駒にチェックを入れる（デフォルトは全件）
3. 生成されたMarkdownのプレビューを確認する
4. 次のいずれかの方法でChatGPTに渡す
   - 「共有する」→ iPhoneの共有シートからChatGPTアプリ等を選ぶ（Web Share API）
   - 「Markdownをコピー」→ ChatGPTに貼り付け
   - 「Markdown/JSONファイルを保存」→ ファイルとして渡す

**ボタンを押すまで外部へは送信されません。** 内容は所持駒の名称・属性・所持数などの事実情報のみで、
画像・駒マスター全件・アプリの内部ログは含まれません。

### 7. 駒情報を補完する（属性・ランク・スキルの調査）

初期状態では、所持駒の属性・ランク・形態・スキルは「不明」です。ホーム画面または所持駒一覧の
「🔎 駒情報を補完」から、ChatGPT等の生成AIを使って不足情報を調べ、取り込むことができます。

1. 「駒情報補完」画面で、調べたい駒にチェックを入れる（「情報不足だけ選択」が便利です）
2. 「AI調査用プロンプトを生成」→ 表示されたプロンプトをコピー
3. ChatGPT等に貼り付けて実行する（**アプリからは何も送信されません**。コピーしてから先はあなたの操作です）
4. ChatGPTの回答（JSON）をコピーし、アプリの「JSONを貼り付ける」に貼り付けて「検証する」
5. 差分（現在の値→AIが返した値）が表示されるので、内容を確認してチェックを入れ、「保存する」

**重要な安全設計:**
- スクリーンショット・アイコン画像・画像特徴量はAIへ一切送信しません（プロンプトはテキストの駒名のみ）
- OpenAI APIやAPIキーは使用しません。コピー＆ペーストで完結します
- AIの回答は厳格に検証されます（HTMLタグ・危険なURL・異常に長い文字列・不明な駒ID・重複などは拒否）
- 補完データは端末内のIndexedDBにのみ保存され、公開されている駒マスターJSON自体は書き換えません

**駒の同一性とAI提案の正式名称について:**
- 駒の同一性は名称ではなく、アプリ内部で管理する一意なpieceIdだけで判定します
- 検索やAI調査に使う「現在の名称」は、マスタ登録済みの正式名称、またはユーザーが仮登録した検索用の
  仮称です。AIが返す名称との**完全一致は要求しません**
- 差分確認画面では、AIの調査結果から「正式名称候補」「二つ名」「バージョン」「進化形態」を並べて表示します
- 正式名称・バージョンの採用（現在の名称の上書き）は、他の項目の承認とは別に**必ず個別にチェックを
  入れて明示的に選んだ場合のみ**反映されます。チェックしなければ現在の名称のまま維持されます

**駒名が曖昧な場合（仮登録駒の名称確認・2段階調査）:**

仮登録駒に「ルシファー」のような略称・愛称を入力した場合、同名の駒には進化・複数の闘化・季節限定版・
コラボ版が存在するため、いきなり性能調査を行うと誤った駒の情報として登録してしまう恐れがあります。
これを避けるため、仮登録駒については名称を確定してから性能調査を行う2段階の調査に対応しています。

1. 「駒情報補完」画面で仮登録駒にチェックを入れ、「🔍 駒名の候補を確認する」を押す
2. 表示されたプロンプトをChatGPT等に貼り付けて実行する（この段階では性能情報は調査しません）
3. 回答のJSONを取り込むと、「一致」「複数候補」「見つかりません」のいずれかとともに、
   確認できた候補（進化・闘化・季節版・コラボ版などをそれぞれ別候補として）がすべて表示されます
4. 表示された候補から正しいものを1件選ぶ（複数候補がある場合、1件に絞り込まれることはありません）
5. 選択した正式名称で、あらためて性能調査用プロンプトが生成されます。以降は通常の調査手順（4.〜5.）
   と同じです

候補が複数存在する（`ambiguous`）間は性能情報を確定・保存することはありません。候補が見つからない
（`not_found`）場合は候補が表示されず、選択もできません。

## データの保存場所と注意事項

- すべてのデータは **この端末のSafari（IndexedDB）内だけ** に保存されます
- GitHubや外部サーバーには、スクリーンショット・所持駒データ・認識履歴のいずれも送信されません
- Safariの「Webサイトデータを消去」を行うと、この端末内のデータは失われます
- 機種変更やPWAの再インストールでもデータは引き継がれません
- **必ず定期的にJSONバックアップを保存してください**
- 認識に使った元スクリーンショットは、認識処理後に恒久保存しません（切り出し画像のサムネイルのみ端末内に保持され、いつでも削除できます）

## 攻略サイトの画像について

- 本リポジトリ・公開物には、攻略サイト（Game8等）の**生アイコン画像を含んでいません**
- 認識に使う「学習済み特徴量」は、**あなた自身が確認したスクリーンショットのアイコン**から
  端末内でのみ生成・保存されるものであり、攻略サイトの画像から生成したものではありません
  （詳細は下記「画像認識の仕組み」）
- 駒マスターの名称・属性・ランク等のメタデータは、現時点では取得元サイトの利用規約・robots.txt等を
  この開発環境から確認できなかったため、**攻略サイトからの自動取得は実装していません**
  （`tools/master-builder/README.md` に詳細と、将来対応する場合の手順を記載しています）
- 出典ページへのリンクを表示する機能は用意していますが、現状のシードデータには出典URLが
  設定されていません（未確認情報を断定表示しないため）

## 画像認識の仕組み（生アイコンを保存しない設計）

数千件規模のマスター画像との総当たり照合をiPhone上で毎回行うと重く、かつ攻略サイトの
生アイコンを大量に保存する必要が生じてしまいます。本アプリは以下の方式でこれを回避しています。

1. **グリッド検出**: 実機スクリーンショット（1290x2796, iPhone 15/16 Pro Max相当）で実測した
   構造（4列、行ピッチ・列位置の周期性、上部フィルターバー下端、下部ナビゲーション上端）を基に、
   画像から自動的にグリッドを推定する。認識開始前にオーバーレイで切り出し枠を表示し、
   ずれている場合はユーザーが開始位置・行間隔・列位置を数値で微調整できる。調整値は
   画面サイズ（幅×高さ）ごとに端末内へ保存され、次回以降は自動的に使われる
2. **空セル・部分表示セルの扱い**: 背景のみのセルは画素値のばらつきから「空セル」として除外する。
   下部ナビゲーションに一部だけ隠れた最終行は「partial」として識別し、自動確定の対象から外す
   （画面端で一部だけ写った駒を誤って確定しないため）
3. **軽量特徴量抽出**: 各セルについて pHash / dHash / aHash（知覚ハッシュ）と色ヒストグラムを
   Web Worker内（UIをブロックしない）で計算する
4. **端末内学習による照合**: あらかじめ用意された「攻略サイトの画像から作った特徴量」は
   使わず、**あなたがこのアプリ上で確認・確定した駒のアイコン特徴量だけ**を学習データとして
   IndexedDBに蓄積し、次回以降の照合に使う（＝権利関係が明確な、ユーザー自身のデータのみ使用）
5. **信頼度判定**: 1位候補と2位候補のスコア差から信頼度を算出し、僅差の場合は自動確定せず
   「要確認」に回す（誤った自動登録を防ぐことを最優先）
6. **スクロール重複除外**: 連続するスクリーンショット間で、行位置がスクロールした一致を検出し、
   二重カウントを防ぐ（同一画像内に同じ駒が複数表示される場合は複数所持として正しくカウントする）

この設計により、**この方式では初回スキャン時は「要確認」が多くなります**（学習データがまだ
ない駒はすべて要確認になります）。1度名前を確定すればその駒は以後自動認識されやすくなります。
これは「認識率」よりも「誤った自動確定をしないこと」を優先する、仕様書の方針に沿った設計判断です。

### 技術選定について

仕様書ではOpenCV.js/WebAssemblyの利用を例示していますが、本実装では以下の理由により
**Canvas 2D APIベースの軽量ハッシュ（pHash/dHash/aHash/色ヒストグラム）** を採用し、
OpenCV.jsやORB等の局所特徴量ライブラリは使用していません。

- OpenCV.jsは数MBの追加ダウンロードが必要で、iPhone Safariでの初回読み込み負荷が大きい
- 「攻略サイトの画像を保存しない」方針上、マッチング対象は少数（ユーザーが確認した駒のみ）であり、
  ORBのような高精度・重量級の局所特徴量マッチングを必要とする規模ではない
- pHash/dHash/aHash+色ヒストグラムの多段階照合でも、「高信頼度のみ自動確定・僅差は要確認」という
  設計方針は十分に実現できる

将来、認識対象や精度要件が拡大した場合は、`src/recognition/` 内のマッチングロジックを
差し替えることでOpenCV.js等への移行が可能な構成にしています。

## 開発者向けセットアップ

### 前提

- Node.js 22系
- npm

### セットアップ

```bash
npm ci
npm run dev       # 開発サーバー起動（http://localhost:5173 ）
```

### ビルド

```bash
npm run build         # ローカル確認用（base: "/"）
npm run build:pages   # GitHub Pages公開用（base: "/othellonia-inventory/"）
```

### テスト

```bash
npm run test           # 単体・結合テスト（Vitest）
npm run test:watch     # watchモード
npm run test:e2e       # E2E（Playwright、iPhone SE/15/15 Pro Max相当のビューポートで実行）
```

Playwright実行前に、対象ブラウザをインストールしていない環境では `npx playwright install chromium`
を実行してください（このリポジトリのCIでは自動実行されます）。

### 公開物の安全性チェック

```bash
npm run check:no-raw-icons   # 生アイコン・大量画像混入チェック
npm run check:secrets        # 秘密情報（APIキー等）混入チェック
npm run check:pwa            # PWA設定（manifest/Service Worker等）チェック
```

### 駒マスター・PWAアイコンの再生成

```bash
npm run master:seed    # 既知データからpublic/master/*.jsonを再生成（ネットワーク不使用）
npm run master:icons   # 自作SVGからPWAアイコンPNGを再生成（ネットワーク不使用）
```

攻略サイトからの自動取得については `tools/master-builder/README.md` を参照してください
（利用規約等が確認できるまで未実装です）。

### ディレクトリ構成

仕様書では `apps/web/` `packages/shared/` 等のモノレポ構成が例示されていますが、本実装では
アプリ規模に対して過剰な分割を避けるため、単一パッケージ内でディレクトリによる責務分離を
行う構成に簡略化しています。

```
src/
  domain/        ドメイン型定義・駒名パース
  db/            IndexedDBアクセス層（idb）
  recognition/   グリッド検出・画像ハッシュ・候補照合・重複除外
  workers/       画像処理用Web Worker
  master/        駒マスター読み込み（public/master/*.jsonをfetch）
  enrichment/    駒情報補完（不足判定・AI調査プロンプト生成・JSON検証・差分計算）
  backup/        バックアップ/復元・AI相談用Markdown/JSON生成・共有処理
  state/         React Context（アプリ全体の状態・進行中スキャンの状態）
  pages/         画面コンポーネント（ホーム/取込/確認/一覧/駒情報補完/AI相談/バックアップ）
  components/    共通UIコンポーネント
public/
  master/        駒マスター・所持駒シードデータ（JSON、事実情報のみ）
  icons/         自作PWAアイコン（source.svgから生成）
tools/
  master-builder/  マスターデータ・アイコン生成スクリプト（PWA本体から分離）
scripts/         CI用の公開物安全性チェックスクリプト
tests/
  unit/          Vitest単体テスト
  integration/   Vitest結合テスト（dist成果物の安全性検証を含む）
  e2e/           Playwright E2Eテスト
.github/workflows/
  ci.yml             lint/型チェック/テスト/ビルド/公開禁止ファイル検査
  deploy.yml         GitHub Pagesへのデプロイ
  master-update.yml  駒マスターデータの手動更新（workflow_dispatch、PR提示のみ）
```

### React Routerについて

GitHub Pagesはサブパス配信かつサーバー側リライトができないため、`BrowserRouter`+404.html
リダイレクトのハックではなく **`HashRouter`** を採用しています（`/#/inventory` のような
URLになります）。これによりリロード時のルーティング崩れやサブパス設定の複雑さを避けています。

## GitHub Pagesへのデプロイ手順

このリポジトリのアプリ本体・テストはこの時点で完成していますが、実際に公開するには
**リポジトリ所有者ご自身によるGitHub操作**が必要です。以下の手順を行ってください
（認証情報やトークンをチャット等に貼り付ける必要はありません）。

1. GitHubにログインする
2. このリポジトリ（`othellonia-inventory`）の Settings → Pages を開く
3. 「Build and deployment」の Source を **「GitHub Actions」** に変更する
4. `main` ブランチへこの内容をマージ/プッシュする（`.github/workflows/deploy.yml` が自動実行されます）
5. Actionsタブでワークフローの成功を確認し、表示される公開URLにアクセスする

以降は `main` ブランチへの変更のたびに自動で再デプロイされます。

## 現在の制約

- 駒マスターの属性・ランク・スキル詳細は、この開発環境から攻略サイトの利用規約等を確認できな
  かったため、現時点では**未確認（"不明"表記）**です。名称のみ既知の43種類＋過去申告4種類を
  初期データとして収録しています
- 画像認識は「ユーザー自身が確認したアイコンの端末内学習」に基づくため、**アプリを使い始めた
  直後は自動確定が少なく、多くが「要確認」になります**（誤認識の自動確定を避けるための意図的な設計です）
- グリッド検出は、実機スクリーンショット2枚（1290x2796, iPhone 15/16 Pro Max相当、所持駒
  合計484件のうち一部を撮影したもの）を用いて実測・検証済みです（4列、行ピッチ約252px、
  上部フィルターバー下端・下部ナビゲーション上端の位置など）。異なる解像度の端末や、UIが
  変更された場合は、認識開始前のオーバーレイ確認画面で自動検出結果を確認し、必要に応じて
  数値を微調整してください（調整値は画面サイズごとに保存され、次回以降は自動的に使われます）
- 上記2枚の実機スクリーンショットはスクロール的に連続しておらず（比較検証の結果、重複0件）、
  「スクロール重複除外」機能そのものは実データでは未検証です（重複が実際に存在するデータでの
  検証はできていません）。ロジック自体は合成データによる単体テストで検証済みです
- OpenCV.js/ORB等の高精度局所特徴量は採用していません（採用理由は上記「技術選定について」）
- 攻略サイトからの自動データ取得（マスター更新の完全自動化）は未実装です
